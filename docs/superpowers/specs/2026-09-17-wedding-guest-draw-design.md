# 婚礼现场宾客分组抽奖系统设计

日期：2026-09-17

状态：待用户最终审阅

## 1. 目标

构建一套面向婚礼现场的单场活动系统。少于 500 名成人宾客通过手机扫描二维码登记，系统根据回答为每人确定一个主抽奖组并附加多个标签。工作人员在后台实时查看统计、处理异常、调整规则和人工改组，随后按主组在投影大屏上抽取中奖宾客。

系统部署在用户拥有的公网服务器和域名下。首版优先保证现场稳定、数据一致、抽奖不重复和故障可恢复，不扩展为通用问卷平台或完整婚庆平台。

## 2. 已确认约束

- 登记发生在婚礼现场，通过公网和可信 HTTPS 访问。
- 成人宾客各自扫码登记；同行儿童只参与统计，不进入奖池。
- 每位成人只有一个主抽奖组，同时可以拥有多个标签。
- 主组规则可以在后台调整优先级、启停并批量重算。
- 管理员可以人工改组并锁定，批量重算不得覆盖锁定结果。
- 重复识别键为“规范化姓名 + 手机号后四位”，不收集完整手机号。
- 全场默认一人最多中奖一次。
- 服务器规模按 500 人以内设计，采用单机 Docker 部署。

## 3. 范围

### 3.1 首版包含

- 婚礼设置：新人姓名、日期、举办省市、登记开放状态、大屏背景照片。
- 登记二维码生成和 PNG 下载。
- 三步式移动端登记、确认、提交、重复记录更新和本地草稿。
- 实时概览、宾客名单、异常记录、分组结果和 CSV 导出。
- 主组、标签、优先级规则、影响预览、一键重算和人工锁组。
- 奖项配置、适用组别、每轮人数、抽奖控制台和投影大屏。
- 服务端随机抽取、候选池快照、防重复中奖、撤销和审计日志。
- 数据备份、脱敏应急名单、健康检查和部署文档。

### 3.2 首版不包含

- 邀请函发送、短信验证码、微信登录或宾客账号。
- 排桌、座位图、菜单选择、祝福墙、照片直播或支付。
- 多场婚礼、多租户和拖拽式问卷编辑器。
- 内定中奖、个人权重或概率调整。

## 4. 技术方案

采用一个全栈应用和一个数据库，避免在 HeyForm、NocoDB、n8n 与独立抽奖站点之间同步现场数据。

| 层级 | 方案 |
| --- | --- |
| Web 应用 | Next.js App Router、TypeScript |
| UI | Tailwind CSS、shadcn/ui、Lucide 图标 |
| 表单 | React Hook Form、Zod |
| 数据库 | PostgreSQL、Prisma |
| 规则 | `CacheControl/json-rules-engine` |
| 图表 | Recharts |
| 二维码 | `qrcode.react` |
| 大屏场景 | Three.js；参考 `LOG1997/log-lottery` 的 MIT 交互设计，中奖逻辑不复用 |
| 实时更新 | HTTP 写入 + Server-Sent Events；断线后重新获取当前状态 |
| 登录 | Better Auth、数据库会话、Argon2 密码哈希 |
| 反向代理 | Caddy 自动管理 HTTPS |
| 部署 | Docker Compose：Caddy、应用、PostgreSQL |

`log-lottery` 的 IndexedDB 名单和客户端抽取方式不进入系统。若移植其隔离的视觉代码，保留 MIT 许可证和第三方声明。大屏只负责呈现服务端已经确定的结果。

## 5. 页面与角色

### 5.1 宾客登记 `/join`

采用已确认的“分步引导”方案：

1. 姓名、手机号后四位、与新人关系。
2. 是否携带儿童；选择儿童人数。
3. 出发省市和最终确认。

每一步写入浏览器本地草稿。最终提交成功后显示主组、现场编号和登记成功状态。提交即代表到场并进入候选池。重复识别键已存在时，页面提示宾客核对并更新原记录，不新增第二条记录。

### 5.2 现场后台 `/admin`

首页采用已确认的“现场指挥台”：展示登记总数、儿童人数、外地人数、各主组人数、最近登记趋势、异常数量、数据库状态和投影连接状态。

独立页面提供：

- 宾客搜索、筛选、编辑、禁用、人工改组、锁组和 CSV 导出。
- 疑似重复和未分组记录处理。
- 主组、标签和规则配置。
- 奖项、轮次、中奖记录和审计日志。
- 备份、应急名单和健康状态。

### 5.3 抽奖控制台 `/draw`

管理员选择奖项、目标主组和中奖人数。页面在开始前显示有效候选人数、已中奖人数和规则更新时间。控制台发出锁定、抽取、公布、取消与撤销命令，但不能直接指定中奖人。

### 5.4 投影大屏 `/screen`

采用已确认的“仪式聚光”方向：婚礼照片全屏展示，姓名居中，组别与奖项作为次级信息。动画前后均不得展示手机号后四位、儿童、来源地或后台控制按钮。

大屏默认只读。刷新、断线或应用重启后，它从服务端恢复当前轮次及已经确定的结果，不重新抽取。

## 6. 数据模型

### 6.1 核心实体

`WeddingSettings`

- 新人姓名、婚礼日期、举办省市、登记开关。
- 大屏背景资源、标题和最后更新时间。

`Guest`

- 内部 UUID、现场编号、姓名原文和规范化姓名。
- 手机号后四位。
- 关系枚举：男方亲属、女方亲属、男方朋友、女方朋友、共同朋友、同事、同学、其他。
- 儿童人数、出发省市、是否外地的派生值。
- 主组 ID、组别锁定状态、启用状态。
- 冲突序号；公开登记固定使用 `0`，只有管理员可以为真实同名冲突创建其他序号。
- 创建时间、更新时间和提交设备的不可逆摘要。
- 唯一索引：规范化姓名、手机号后四位与冲突序号。

`Group`、`Tag`、`GuestTag`

- 主组包含名称、颜色、排序和启用状态。
- 标签为多对多关系，用于统计和筛选，不直接决定候选池。

`GroupingRule`

- 名称、启用状态、优先级、JSON 条件、目标主组和附加标签。
- 规则版本、创建者和更新时间。

`Prize`

- 名称、图片、允许的主组、计划中奖人数、排序和启用状态。

`DrawRound`

- 奖项、目标组、计划人数、状态、算法版本和操作者。
- 状态：`PREPARING`、`LOCKED`、`DRAWN`、`PUBLISHED`、`CANCELLED`。
- 锁定、抽取、公布、取消时间和撤销原因。

`DrawCandidateSnapshot`、`Winner`

- 快照保存每轮锁定时的候选宾客 ID 和必要的显示字段。
- 中奖记录关联轮次、宾客、奖项、公布时间和状态。
- 中奖状态为 `RESERVED`、`PUBLISHED` 或 `REVOKED`。数据库通过部分唯一索引保证每位宾客最多存在一条未撤销中奖记录。

`AdminUser`、`Session`、`AuditEvent`

- 管理员、数据库会话和只追加审计记录。
- 审计事件保存操作者、动作、对象、时间、前后差异和理由。

## 7. 分组规则

### 7.1 默认主组规则

规则按数字优先级从高到低执行，第一个命中的启用规则确定主组：

1. 儿童人数大于 0 → 亲子宾客组。
2. 出发城市不同于举办城市 → 远道宾客组。
3. 男方亲属或男方朋友 → 男方亲友组。
4. 女方亲属或女方朋友 → 女方亲友组。
5. 共同朋友、同事或同学 → 共同好友组。
6. 其他 → 其他宾客组。

标签独立计算，例如“带小朋友”“外地宾客”“男方亲友”“女方亲友”“同事”“同学”。因此一个被分入亲子组的外地男方亲属仍保留“外地宾客”和“男方亲友”标签。

### 7.2 规则变更

后台允许修改优先级、条件、目标组和启用状态。保存配置不立即修改宾客。管理员必须先运行影响预览，查看各组人数变化和受影响名单，再确认批量重算。

重算在数据库事务中按固定规则版本执行。锁组宾客保持原组。没有规则命中的宾客进入异常队列，不具备抽奖资格，直到管理员处理。

## 8. 抽奖设计

### 8.1 候选资格

候选人必须同时满足：

- 已完成现场登记。
- 已分配启用的主组。
- 宾客记录处于启用状态。
- 位于本轮目标主组或奖项允许的组内。
- 没有 `RESERVED` 或 `PUBLISHED` 中奖记录。
- 已进入本轮锁定的候选快照。

儿童不建立候选记录。宾客登记、资料编辑或规则重算不会改变已锁定轮次的快照。

### 8.2 状态和并发

1. 管理员创建准备中的轮次。
2. 服务端在事务中查询资格并写入候选快照，然后设为 `LOCKED`。
3. 服务端使用 Node 加密随机源和无放回抽样产生结果，同时写入 `RESERVED` 中奖记录，再将轮次设为 `DRAWN`。
4. 大屏播放动画并读取已经写入的结果。
5. 管理员公布后设为 `PUBLISHED`，中奖资格正式生效。

轮次行使用数据库锁和版本字段。重复点击、网络重试或两名管理员同时操作时，只有一个符合当前状态的命令成功。所有命令带幂等键。

`RESERVED` 状态立即排除其他轮次，因此两个并行轮次也不能抽中同一宾客。取消未公布轮次会将预占记录改为 `REVOKED`，释放资格；公布则改为 `PUBLISHED`。已公布结果只能由管理员撤销，必须填写原因，并记录审计事件。抽奖大屏不提供内定或个人权重接口。

## 9. 实时同步

宾客提交和管理员命令使用普通 HTTPS 请求。后台、控制台和大屏通过 SSE 接收计数变化、异常变化、连接状态和当前轮次事件。

首版只运行一个应用实例，因此采用进程内事件广播。SSE 断线后浏览器自动重连，并携带事件序号；若事件历史已过期，客户端重新读取完整快照。应用重启后，当前状态从 PostgreSQL 恢复。

投影连接心跳和最后响应时间显示在后台。投影断线不阻塞抽取，但控制台必须明确提示，避免主持人在大屏未连接时公布。

## 10. 安全与隐私

- 公网只开放 `80/443`；PostgreSQL 和应用内部端口不对公网开放。
- Caddy 将 HTTP 重定向到 HTTPS，并自动续期证书。
- 管理页面使用数据库会话、`HttpOnly`、`Secure`、`SameSite` Cookie。
- 管理密码以 Argon2 哈希保存；密钥和初始管理员凭据来自环境变量。
- 所有表单和 API 输入通过 Zod 校验，数据库查询使用 ORM 参数化。
- 写请求执行 CSRF 检查；公开登记端点按 IP 和设备摘要限速。
- 手机号后四位不写入访问日志，不进入大屏、普通统计或脱敏导出。
- CSV 导出和中奖撤销要求近期管理员认证。
- 审计日志为只追加数据，普通后台没有删除入口。

系统不声称手机号后四位能完成强身份验证。它只用于现场低敏去重。合法的同名同后四位冲突由管理员在异常页建立带独立冲突序号的第二条记录；公开提交始终匹配冲突序号 `0` 的原记录。

## 11. 故障恢复

- 移动端每步保存本地草稿，成功提交后清除。
- 最终提交带幂等键；超时重试返回同一结果。
- 抽奖先持久化结果，再播放动画。大屏重连后恢复同一结果。
- 每次正式抽奖前生成数据库备份和脱敏 CSV 应急名单。
- PostgreSQL 数据卷每日备份，婚礼当天每小时生成快照。
- 上传的背景照片放入持久卷，并随备份清单保存。
- `/health` 同时检查应用和数据库；后台展示健康状态。
- 应急名单可以在备用电脑上离线抽取，但离线结果需要在系统恢复后人工登记并注明理由。

## 12. 视觉方向

- 大屏：仪式聚光。真实婚礼照片全屏，不使用装饰性渐变背景；姓名为第一视觉层级。
- 手机：分步引导。每屏一个主题，大字号、大触控区域和明确进度。
- 后台：现场指挥台。首屏优先展示整体状态、异常和大屏连接，名单为独立工作页。
- 后台保持高信息密度和清晰状态色，不使用营销式大标题或多层嵌套卡片。
- 所有固定格式区域使用稳定尺寸，避免姓名、加载状态或数字变化造成布局跳动。

## 13. 测试

### 13.1 自动化测试

- 单元测试：姓名规范化、后四位校验、重复键、派生标签、规则优先级、锁组、候选资格和抽样边界。
- 集成测试：重复提交更新、规则预览与重算、轮次状态机、并发开奖、幂等、撤销、认证和审计。
- 端到端测试：登记 → 实时后台 → 自动分组 → 锁定候选 → 抽取 → 大屏公布 → 后续排除。
- Playwright 覆盖移动端 Safari 等效尺寸、Android Chrome 尺寸、桌面 Chrome/Edge 和 1920×1080 投影。
- 使用 k6 模拟 500 名宾客在 5 分钟内完成登记，同时保持后台和大屏 SSE 连接。

随机性测试只验证中奖者属于快照、人数正确、没有重复和状态一致，不用一次测试的分布推断随机质量。

### 13.2 故障测试

- 提交时断网和重复点击。
- 后台或大屏刷新、SSE 断线重连。
- 抽取请求超时后重试。
- 应用容器在 `DRAWN` 后、`PUBLISHED` 前重启。
- PostgreSQL 备份恢复和上传资源恢复。

## 14. 婚礼前验收

1. 导入或生成 100 条脱敏宾客数据。
2. 调整规则，核对预览和实际重算结果。
3. 连续执行所有奖项彩排，确认无人重复中奖。
4. 验证取消、撤销和审计记录。
5. 更换电脑打开大屏，验证当前轮次恢复。
6. 完成数据库备份与恢复演练。
7. 在实际投影设备和手机网络上完成全流程。
8. 清除测试数据，锁定正式规则并生成正式二维码。

首版完成标准：关键端到端测试全部通过；500 人集中提交压力测试通过；数据库恢复成功；实际投影无布局重叠；正式彩排完成。

## 15. 实施边界

实施按单体应用内部模块拆分，而不是部署为多个服务：

- `registration`：登记、草稿协议、去重和修改。
- `grouping`：主组、标签、规则、预览和重算。
- `guests`：名单、异常、人工改组和导出。
- `drawing`：奖项、轮次、候选快照、抽样和中奖记录。
- `live`：SSE 事件和状态恢复。
- `admin`：认证、设置、审计、备份和健康检查。
- `screen`：投影视觉场景和结果呈现。

模块通过服务层和数据库事务协作。抽奖模块不得依赖浏览器本地名单；规则模块不得直接修改已锁定候选快照；大屏模块不得拥有抽取权限。
