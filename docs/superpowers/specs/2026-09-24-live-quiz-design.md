# 婚礼现场同步答题功能设计

日期：2026-09-24

状态：已按用户确认的规则形成执行设计，实施前可复核

## 1. 目标

在现有婚礼宾客登记、分组和抽奖系统中加入一场由主持人控制的同步答题活动：宾客使用登记后获得的身份继续参与答题；主持人在大屏逐题展示题目并开始统一倒计时；每题结束后才公布答案；最终成绩写回宾客记录，并作为抽奖候选资格的可调分数门槛。

## 2. 已确认规则

- 题目数量固定为 10 题，每题 1 分，总分 10 分。
- 必须先完成现有宾客登记，答题使用同一宾客身份，不另建账号体系。
- 主持人逐题开始；题目开始时服务器生成统一的 `opensAt` 和 `closesAt`。
- 每题默认限时 30 秒，后台可修改整场默认值；建议允许发布前逐题覆盖。
- 每题只能提交一次，提交后不可修改。
- 迟到、掉线或超过截止时间的宾客跳过本题，不补答；后续题目仍可参加。
- 当前题关闭后，主持人才能公布正确答案和解析；答案不会在题目开放事件中发送给宾客端。
- 10 题结束后，成绩保存到宾客答题记录和宾客汇总字段。
- 抽奖先按分数阈值筛选：默认从后台设定的阈值开始；某组候选人数小于奖品名额时，每次下调 1 分，最低到 0 分。
- 降到 0 分仍不足时，只抽现有候选人，中奖人数不超过候选人数，并记录实际阈值和回退过程。
- 答题成绩只影响配置为“需要答题成绩”的抽奖轮次；普通抽奖仍可按原有资格运行。

## 3. 非目标

- 不做通用问卷编辑器、题库导入、复杂题型或宾客账号注册。
- 首版只支持单选题；题干、四个选项、正确选项和解析由管理员配置。
- 不允许客户端自行开始、暂停、延长、公布答案或修改成绩。
- 不把正确答案提前下发到浏览器，也不依赖客户端时钟判断资格。

## 4. 推荐架构

采用数据库持久化的答题场次状态机，加现有进程内 SSE 广播。数据库是真实状态源，SSE 只负责低延迟通知；刷新、断线和应用重启都通过数据库快照恢复。

答题场次状态：`DRAFT -> READY -> LIVE -> REVIEW -> FINISHED -> CANCELLED`。

- `DRAFT`：管理员编辑题目和配置。
- `READY`：题目完整且已发布，等待主持人开始第一题。
- `LIVE`：当前题开放，服务器控制截止时间。
- `REVIEW`：当前题收卷完成，主持人公布答案；公布前宾客端只看到“本题已结束”。
- `FINISHED`：10 题结束，成绩已汇总。
- `CANCELLED`：整场作废，不写入有效抽奖成绩。

每个状态转换带版本号和幂等键，使用 Serializable 事务或条件更新防止主持人重复点击、两个后台标签页并发操作和网络重试造成状态倒退。

## 5. 身份绑定

登记成功后服务端签发一个随机、不可预测的 `quizParticipantToken`，只保存其哈希；原始 token 放入 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie。答题 API 只接受该 token 对应的宾客，不接受前端传入任意 `guestId`。

登记更新同一宾客时保留其 token；管理员禁用宾客时立即使 token 失效。答题页面只能从登记成功页或二维码入口进入，未登记用户显示“请先完成登记”。这不是强身份认证，现场模型仍以登记信息为低敏去重依据。

## 6. 数据模型

新增实体：

- `QuizSession`：场次配置、状态、当前题序、默认限时、发布/结束时间、版本。
- `QuizQuestion`：场次内序号、题干、四个选项、正确选项、解析、启用状态。
- `QuizParticipant`：场次与宾客关联、token 哈希、参与状态、总分、答题完成时间。
- `QuizAnswer`：每题一次提交，提交时间、是否迟到、选择项、得分、客户端请求幂等键；`(participantId, questionId)` 唯一。
- `QuizScoreSummary` 可不单独建表，首版将最终分数和完成状态写入 `Guest.quizScore`、`Guest.quizSessionId`；若未来支持多场，再迁移为独立汇总表。

为抽奖增加可选筛选字段：`DrawRound.scoreThreshold`、`DrawRound.scoreFallbackStep`、`DrawRound.scoreFallbackUsed`，并把锁定时实际采用的阈值写入候选快照，确保抽奖结果可审计、可复现。

## 7. 实时数据流

主持人后台命令：

1. 创建/编辑题目并发布场次。
2. `start-question`：事务锁定当前题，写入 `opensAt`、`closesAt`，广播 `quiz.question_opened`。
3. `close-question`：服务器确认到期或主持人执行提前收卷，状态转 `REVIEW`，广播不含答案的 `quiz.question_closed`。
4. `publish-answer`：仅后台读取正确答案并广播 `quiz.answer_published`；宾客端此时显示答案和个人得分。
5. `finish-session`：最后一题公布后计算汇总分，写回 Guest，广播 `quiz.finished`。

宾客端只接收当前题序、题干、选项、服务器截止时间、当前状态和公布后的答案；不接收未来题目或未公布答案。答题提交由服务端比较请求到达时间与 `closesAt`，晚到统一返回 `QUESTION_CLOSED`。

## 8. 抽奖资格

默认行为保持现有抽奖不变。启用成绩筛选的轮次在锁定候选时：

1. 读取目标组内已登记、启用、未中奖且已完成答题的宾客。
2. 从配置阈值开始筛选 `quizScore >= threshold`。
3. 候选少于奖品名额时，事务内按 1 分递减直到 0 分或人数足够。
4. 仍不足时锁定全部符合最低阈值的候选，并把 `actualThreshold`、回退次数、候选数写入轮次和审计日志。
5. 候选快照保存分数和实际阈值，之后修改宾客成绩或规则不影响已锁定轮次。

未完成答题的宾客不进入“需要答题成绩”的轮次；管理员可以在后台明确选择“允许未完成者按 0 分参与”，默认关闭。

## 9. 界面

- `/quiz`：宾客移动端，展示登记身份、当前题、倒计时、选项、提交状态、断线提示和公布答案后的得分；禁止返回修改已提交答案。
- `/admin/quiz`：题目编辑、限时、发布、当前状态、参与人数、提交人数、异常和成绩分布；主持人控制逐题开始/收卷/公布/结束。
- `/screen`：增加答题场景，在题目开放时显示题干和选项，在收卷时显示“等待公布答案”，公布后显示正确答案/解析；答题结束后恢复抽奖场景。
- `/admin/draw`：增加“启用答题成绩筛选”、初始阈值、回退开关和实际阈值预览。

## 10. 故障与安全

- 服务器时间是唯一计时依据；客户端只做视觉倒计时。
- 迟到请求返回明确状态，不能通过重试获得补答机会。
- 提交接口使用幂等键；重复提交返回第一次结果。
- SSE 断线后先读快照再重连，不能根据本地缓存自动提交。
- 题目开放事件不包含正确选项；服务端序列化层增加字段白名单测试。
- 管理命令全部写审计日志；成绩重算、场次取消和手工改分需要管理员确认并填写原因。
- 正确答案和解析不进入公开日志、页面源代码或未来题目响应。

## 11. 验收标准

- 500 名宾客在 5 分钟内完成登记后可稳定进入同一场答题。
- 同一题在 30 秒截止点前后提交，服务端结果严格分为成功和跳过。
- 每个宾客每题最多一条答案；刷新、重复点击、重连不产生第二次得分。
- 主持人未公布前，宾客端和大屏均看不到正确答案。
- 场次重启后恢复当前题状态、截止时间和已保存答案。
- 10 题成绩正确写回宾客，并能在后台按组、分数和完成状态筛选。
- 抽奖阈值逐分回退、最低 0 分和候选不足行为都有自动化测试及审计记录。
